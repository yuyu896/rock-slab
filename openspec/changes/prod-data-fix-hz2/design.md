# design — 2分杭州资产整清（合体形态）

## Context

两种已验证形态在同一分公司的组合（均为本日生产实测）：

| 侧 | 数据 | 来源 | 路径 |
|---|---|---|---|
| 实例 | 88 实例全在库（手机41+一体机47），镜像零差异 | 1 张纯实例行已入库采购单 CG20260915-009 | 出生单连删（0914 温州模式） |
| 建账 | 数量 19 行(436) + 耗材 21 行(665) | 40 张建账调整单 | 成对删除（nb32 模式的管理方式过滤面=全部非实例品目） |

员工 1 人、无其他单据。两侧数学独立（实例品目调整单为 0，实例库存全由采购单解释；非实例库存全由调整单解释），同事务组合后 replay 与 stored 双双归零，对账自洽。

## Decisions

### D1. 单事务合体执行

一个 `transaction.atomic()` 内先实例侧（链接→实例→单据→回退）后建账侧（调整单+行成对删）。两侧无共享行（品目管理方式互斥），删除顺序不敏感；合并为单事务使"整分公司资产归零"成为原子操作——任一侧断言失败整体回滚，不出现"实例删了建账还在"的半程态。

### D2. 助手复用与断言搬运

- 算量/回退/删除顺序：复用 0914 的 `_transfer_ledger_plan` / `_rollback_ledger`（本案采购单全 +在库 计划，逐条回退无负值风险，无需聚合）/ `_delete_transfer_with_born_instances`。
- 镜像三列断言：复用 0915 的 `_assert_in_stock_mirror`。
- 建账侧边界断言沿用 nb32：非实例品目无流转单据行（本案全部单据即实例出生单，删除后分公司零单据）、无错挂实例。

### D3. 命令形态沿用

常量固化（分公司名）、dry-run/`--apply`、末尾内嵌对账复验、幂等（实例与建账两侧均空时跳过）。

## Risks / Trade-offs

- [半程态] → 单事务原子性，断言前置
- [误伤其他分公司] → 作用域全部以 branch=2分杭州 收敛；dry-run 打印单号/回退量/行清单
- [员工后续重导] → 节点/员工/字典/发号序列保留，导入路径无阻碍

## Migration Plan

部署 → 备份 → dry-run 复核 → `--apply` → 独立对账 + 抽查（实例 0、三品目台账 0、员工在）→ 幂等复证。回滚走备份整库还原。
