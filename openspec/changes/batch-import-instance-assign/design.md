## Context

当前系统支持批量导入领用单，但仅对数量管理品目有效。实例管理品目（如电脑、手机）因 Excel 模板缺少指定内部编号的机制，导入时预检会拒绝（[services.py:172-173](backend/apps/transfers/services.py#L172-L173)）。

现有校验架构完备：`validate_line_items_instances` 已覆盖实例状态、品目匹配、分公司归属、单据占用等所有规则，无需修改。

## Goals / Non-Goals

**Goals:**
- 支持批量导入领用单时通过内部编号指定实例
- 保持数量管理品目导入流程不变
- 复用现有校验逻辑，不引入新规则

**Non-Goals:**
- 不修改其他单据类型（调拨、回收）的批量导入
- 不支持 FIFO 自动分配实例（用户必须显式指定）
- 不改变实例管理的核心约束（一行一机器，数量=1）

## Decisions

### 决策 1：一行一实例，而非逗号分隔

**选择**：每行填一个内部编号，数量固定为 1<br>
**替代方案**：一行填多个编号（如 `HZ001,HZ002`），数量与编号个数一致

**理由**：
- Excel 单元格解析简单，无需处理分隔符容错（逗号/分号/空格）
- 校验错误定位精确到行
- 与数量品导入习惯一致（3 台 = 3 行）
- 实例管理品目本质是"台账化"，一行一台符合直觉

### 决策 2：编号列对数量品留空，而非新增操作类型

**选择**：在同一模板中增加「内部编号」列，数量品留空，实例品填写<br>
**替代方案**：为实例品创建单独的导入模板/操作类型

**理由**：
- 实际业务中常混合导入（如同时领用办公椅和电脑）
- 品目管理方式由字典决定，用户无需关心区分逻辑
- 单一模板降低学习成本
- 表头守卫同时接受旧版无「内部编号」列的领用模板，旧模板继续用于数量管理品目

### 决策 3：编号查询锁品目表，而非锁实例表

**选择**：先 `lock_line_item_categories` 锁品目，再按编号查询实例并 `lock_line_item_instances` 锁实例<br>
**理由**：与现有流程一致（[views.py:1521-1528](backend/apps/transfers/views.py#L1521-L1528)），避免死锁风险

### 决策 4：复用单据创建的实例查看权限

**选择**：锁定并重读品目后，如导入行属于实例管理品目，要求操作者具有 `view_instances`；随后锁定被引用实例并调用现有校验器。<br>
**理由**：权限目录已将查看实例档案列为实例管理单据的条件前置权限，批量导入也创建同类单据。

## Risks / Trade-offs

### 风险 1：编号输入错误率
**风险**：用户手工填写编号时可能打错（如 HZ001 误写为 HZ010）<br>
**缓解**：校验层报错提示准确到行和编号，用户可立即纠正

### 风险 2：批量导入时占用检测非终检
**风险**：导入时检测未生效单据占用（[services.py:180](backend/apps/transfers/services.py#L180)），但提交前账面可能变动<br>
**现状**：此为现有架构特性，生效时行锁终检兜底（ledger.py），本次不改变

### Trade-off：无自动分配便利性
**取舍**：不支持"领用 3 台电脑，系统自动选"的场景<br>
**判断**：实例管理的价值在于精确追踪，自动分配与此理念冲突
