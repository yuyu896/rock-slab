## Context

实例档案图片当前保存在 `fixed_assets/`，存储名可能沿用上传文件名。覆盖时先删除旧文件，再保存新文件；同名上传可能复用旧 URL。图片接口和查询接口返回 `ImageField` URL，前端将其原样交给 `el-image`，同一 URL 不会触发新的图片资源请求。生产媒体图片按现有 Nginx 规范缓存 7 天，因此只替换相同路径下的文件无法可靠刷新各设备缓存。

## Goals / Non-Goals

**Goals:**

- 每次图片更新都让客户端得到不同的、可持续读取的图片 URL。
- 让首次读取现有图片的客户端离开旧的无版本 URL 缓存键。
- 替换失败时保留当前图片；成功后清理旧文件。
- 保留现有图片校验、权限、接口形状和媒体缓存策略。

**Non-Goals:**

- 不关闭全局图片缓存或修改图片 7 天缓存策略。
- 不改变实例图片的权限、媒体访问控制、大小和格式限制。
- 不扩展到头像、品目图片或其他文件上传流程。
- 不生成缩略图、转换图片格式或批量重写所有现有图片文件。

## Decisions

### D1：使用不可复用文件路径与持久化图片版本

每次上传生成新的随机存储名，例如 `fixed_assets/<asset-id>/<random-id>.<validated-extension>`，不再以原始文件名作为对象键。为 `FixedAsset` 增加图片版本字段，旧记录以 `0` 初始化；每次成功替换或删除图片时递增。序列化器在非空图片 URL 上附加该版本，例如 `?v=3`。

随机路径保证未来版本不会覆盖已有媒体对象；版本参数让部署后现有图片的 URL 从未带版本的形式切换为带版本形式，避免客户端继续使用旧缓存键。版本只随图片变化，不使用通用 `updated_at`，避免普通档案编辑导致图片缓存失效。前端继续使用 API 返回的 `图片` URL，不自行拼接临时时间戳。

### D2：先保存并切换到新图，再清理旧图

先完成上传校验，再为新文件创建唯一存储对象。在数据库事务中锁定目标档案、更新图片路径和图片版本；事务提交后再删除旧文件。若数据库更新失败，则清理新文件并保留原记录和旧文件。相同档案的并发替换通过行锁串行化，避免一次替换误删另一次刚保存的文件。

删除图片时先在数据库事务中清空图片引用并递增版本，事务提交后再删除旧文件。文件删除失败可能留下孤立文件，但不能让数据库指向已删除文件；清理失败应记录日志以便后续清理。

### D3：保留现有 7 天缓存策略

`nginx-reverse-proxy` 已规定图片缓存 7 天。版本参数和不可复用路径使新图拥有新的缓存键，因此不需要通过全局 `no-store` 牺牲静态图片缓存。部署验证需确认实际客户端和代理按完整 URL 区分带版本参数的图片地址；未来版本还由新的文件路径保障。

### D4：回归测试覆盖同名替换与失败路径

后端测试连续上传同名文件，检查每次成功后的图片 URL 均变化，查询接口返回当前 URL，旧文件仅在成功切换后删除；数据库更新失败时当前数据库引用及旧文件仍保留，新文件被清理。前端测试确认成功响应中的新 URL 被同步到列表和预览。

## Risks / Trade-offs

- [图片版本字段需要数据库迁移] → 使用非空整数字段并为既有记录设置默认值 `0`；迁移不改动图片文件。
- [提交后的旧文件删除失败会留下孤立文件] → 记录清理失败并保留可重试的清理路径；不能为追求无孤儿而提前删除旧图。
- [反向代理可能忽略查询参数作为缓存键] → 未来每次更新还会更换文件路径；部署时验证现有图片的版本查询参数能绕过旧缓存。
- [并发图片替换可能交错] → 在同一数据库事务中锁定档案行，并在事务提交后执行旧文件清理。

## Migration Plan

1. 新增图片版本字段迁移，现有记录默认版本为 `0`；序列化器立即为现有图片 URL 加上版本参数，使客户端取得新的缓存键。
2. 部署唯一存储路径、事务替换/删除逻辑以及 URL 序列化变更；无需批量移动现有媒体文件，也无需改 Nginx 缓存时长。
3. 使用同名图片替换验证上传响应、列表/详情重新查询、浏览器缓存和失败回退。
4. 回滚代码时不反向删除图片版本字段。旧代码仍可读取数据库中的新文件路径；避免在回滚时删除仍被引用的媒体文件。
