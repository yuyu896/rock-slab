## Context

生产实例档案图片目前以单个 `ImageField` 保存并直接用于列表和预览。生产媒体目录已有 7,032 张图片、约 4.57 GB；列表默认每页 50 条，虽然缩略显示为 40×40，浏览器仍下载对应原图。当前上传校验允许单图最大 10 MB，但没有压缩或缩略图处理。

实例图片已有独立上传/删除端点、随机路径、`image_version` 版本 URL 和事务提交后清理旧文件的机制。生产两层 Nginx 中，内层代理可能用自身 HTTP scheme 覆盖外层 HTTPS 协议头，导致 Django 生成 HTTP 媒体 URL。

## Goals / Non-Goals

**Goals:**

- 保留部署前已有实例图片文件，并为其可重试地生成列表缩略图。
- 新上传在发送前尽量压缩，服务端保证最终只保存压缩主图和缩略图，不保留新上传原件。
- 列表按需加载缩略图，图片预览继续显示主图；缩略图未生成时可回退至主图。
- 图片替换/删除期间主图与缩略图保持一致，并维持现有图片版本和失败回退语义。
- 让 Django 在受信任的反向代理链后识别外部 HTTPS scheme。

**Non-Goals:**

- 不重编码、覆盖、移动或删除部署前已有的原图。
- 不处理品目图片、用户头像、移动端图片或 Excel 图片导出。
- 不调整实例档案查询、分页及其 15 秒 API 超时。
- 不改变实例图片的权限、单实例单图语义或现有 10 MB 上传输入上限。

## Decisions

### D1：主图字段保持现有 API 语义，新增可空缩略图字段

保留 `FixedAsset.image` 作为主图和既有 `图片` API 字段，新增可空缩略图存储字段，API 输出 `缩略图` URL。两个 URL 都附加现有 `image_version`。旧数据的 `image` 路径不变，缩略图字段初始为空；存量缩略图使用独立、不可复用的文件路径。

相比替换 `image` 字段或将小图编码进列表 JSON，这种方式保持现有主图接口兼容，也能让列表单独下载较小媒体文件。

### D2：以 WebP 作为新上传的压缩主图和缩略图格式

图片仅用于查看。浏览器在源图最长边超过 2048 像素或文件超过 1 MB 时，先将图片按比例缩放到最长边不超过 2048 像素并转为 WebP，质量初值为 82，以减少上传字节数。服务端使用 Pillow 校验真实图片内容、解码像素上限和尺寸；不符合输出约束的输入由服务端规范化。已经符合约束的浏览器 WebP 可直接作为主图保存，避免重复有损编码。服务端不得保留新上传的原始文件。

每张新主图生成一张最长边不超过 240 像素、保持原始比例的 WebP 缩略图，质量初值为 75，不放大图片。参数先作为提案默认值，验收抽样应检查图片整体辨识度及标签/序列号的可读性。

只做服务端压缩不能减少上传过程的网络字节，因此前端预压缩用于上传速度；服务端规范化用于保证 API 和其他客户端上传的存储约束。

### D3：列表和预览请求不同的图片 URL

实例列表使用 `缩略图` URL，并采用元素进入可视区域时加载的方式。用户点击缩略图时，预览组件使用 `图片` 主图 URL。缩略图字段为空时，前端使用主图作为兼容回退；无主图时继续显示占位符。

浏览器仍以独立媒体请求下载图片，API 仅返回两个版本化 URL。继续沿用现有图片缓存策略和 `image_version`，不通过降低缓存时长或把图片二进制塞入 JSON 解决加载问题。

### D4：存量缩略图使用可重试的批量命令

新增幂等管理命令，按批处理已有实例图片：只从原图生成缩略图，不修改 `image`、`image_version` 或任何业务字段；已有缩略图跳过，单图失败记入汇总并继续处理。命令支持先预览统计与显式执行，避免无意对生产媒体目录批量写入。API 对未生成缩略图的记录返回空 `缩略图`，前端回退主图。

为所有旧图片在读取列表时即时生成缩略图会把不可控的 CPU/磁盘工作放入用户请求，因此不采用请求时自动处理。

### D5：替换和删除同时处理两个媒体文件

上传时先在存储中创建唯一主图和缩略图，再在同一数据库事务内锁定档案、更新两个引用并递增 `image_version`。事务提交后清理旧主图和旧缩略图；任一新文件处理或数据库提交失败时，保留原引用和原文件，并清理未引用的新文件。删除时在事务内同时清空两个引用并递增版本，提交后再清理对应文件。

该顺序延续现有单图安全替换约定，并避免出现列表缩略图与预览主图属于不同上传版本。

### D6：保持可信代理链中的 HTTPS 协议

公网入口 Nginx 依据实际连接 scheme 写入 `X-Forwarded-Proto`。内层 rock-slab Nginx 位于受信任代理之后，转发该头给 Django 时不得用自己的 `$scheme` 覆盖它。Django 继续使用现有 `SECURE_PROXY_SSL_HEADER`。部署验证同时检查 API 返回的绝对媒体 URL 使用 HTTPS。

### D7：回填与部署采用向前兼容顺序

先部署可空缩略图字段、双 URL 输出及主图回退，再部署双文件上传与前端缩略图展示。数据库迁移不得移动现有文件。回填命令完成后，列表自然改为使用缩略图；执行期间未回填记录继续显示原图。回滚代码时保留数据库字段和全部媒体文件，不执行删除或反向清理。

## Risks / Trade-offs

- [存量回填会增加磁盘占用并消耗 CPU] → 分批运行、支持预览/重试，并输出成功/跳过/失败统计；不重写已有原图。
- [WebP 有损压缩可能降低细节] → 初始参数在代表性图片上抽样验收；上传后预览使用压缩主图，失败的验收结果先调整质量或尺寸参数。
- [部分浏览器或其他 API 客户端不做前端预压缩] → 服务端作为最终校验与压缩兜底，继续执行输入大小和解码像素限制。
- [双文件写入可能留下孤儿文件] → 两个新文件均保存成功后才更新数据库；失败路径清理新文件，旧文件仅在事务提交后清理并记录清理失败。
- [旧记录缩略图为空时仍会下载原图] → 保留明确的主图回退以保证可用性，并通过回填汇总跟踪覆盖率。
- [代理头误信任外部输入会造成 scheme 欺骗] → 公网入口覆盖客户端提供的协议头，只有受信任的内层代理保留入口设置的值。

## Migration Plan

1. 增加可空缩略图字段，不改写现有图片路径；扩展序列化器返回版本化 `图片` 与可空 `缩略图`。
2. 部署服务端图片规范化、双文件安全替换和前端按需缩略图展示，同时保留无缩略图回退。
3. 修正内层反向代理协议头转发并验证 HTTPS 图片 URL。
4. 在生产使用预览模式检查待处理数量后，分批生成存量缩略图；检查失败项并可重复执行。
5. 抽样比较原图与新上传压缩主图，检查列表与点击预览的 Network 图片请求大小、缓存版本和实际加载表现。

回滚时旧代码继续读取 `image` 主图字段；不得通过迁移回滚删除已被引用的主图或缩略图文件。新增主图为压缩 WebP 是有意的数据格式变化，回滚不会恢复被丢弃的新上传原件。

## Open Questions

无阻塞问题。2048/240 像素与质量 82/75 为首轮默认参数，最终值以代表性资产照片的验收结果为准。
