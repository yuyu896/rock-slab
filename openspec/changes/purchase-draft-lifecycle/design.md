## Context

草稿现状（2026-09-21 探讨定案）：唯一真实入口是撤回；创建无入口。既有机制：create action 收 `draft` 参数置草稿（views.py:170）；signals 对非待审批单不发创建通知（signals.py:81 守卫）；列表页内排序待审批→草稿置顶第二；stats 为前端 computed（页内口径）。

## Goals / Non-Goals

**Goals:** 草稿生命周期闭环——创建可暂存、撤回直达编辑、数量可见。

**Non-Goals:** 不做草稿提醒/催办；不改其他四种单据（只采购）；不修 stats 页内口径的既有 quirk（见 Risks）；不动后端。

## Decisions

| 决定 | 理由 |
|------|------|
| 存草稿按钮与提交并列（次级样式） | 主行动仍是提交；存草稿是备选。复用同一校验（行满品目+数量） |
| 撤回成功后直接 `startEdit('draft')` | 撤回的目的就是改；确认弹窗在前一隔已防误触，不会「撤错了直接进编辑」——撤回本身已确认过 |
| 草稿卡走前端 computed | 与现有四张卡同机制；后端 stats 接口不动，回归面最小 |
| 编辑表单不动 | 草稿编辑入口已有（详情页草稿态「修改」） |

## Risks / Trade-offs

- [既有 quirk：统计卡为当前页口径非全量] → 现状如此（pending/approved 同口径），草稿卡保持一致不在本变更修正；如实告知用户
- [草稿堆积无人处理] → 草稿卡即观测入口；不做自动清理（业务无此诉求）
- [移动端无存草稿入口] → 移动端采购提交页保持即时提交语义，PC 暂存已覆盖场景；后续有诉求另议
- 回归面：vitest 全量（草稿建单后端用例既有）、build；新增前端用例覆盖双按钮与撤回后 editing 状态
