
# 设计：采购入库单自助撤回 + Excel 表格改版

## Context

- 采购单生命周期既有五态：`草稿 → 待审批 → 已通过/已驳回 → 已入库`；`submit`（草稿→待审批）、`resubmit`（已驳回→待审批）、编辑（仅已驳回）、删除（草稿/待审批/已驳回）均已存在
- `TransferLine.供应商` 行级字段已存在（models.py:196，verbose「行级，空=继承单头」），表头 `Transfer.供应商` 亦在——数据模型无需变更
- 单据纪律：`待审批` 单尚未写台账（入库在已通过后的 warehousing 步骤），撤回不触碰台账
- 前端 `PurchaseDetail.vue` 为分块表单样式，供应商在表头（extra-item 展示 + 编辑表单项）

## Goals / Non-Goals

**Goals:**

- 创建人可把「待审批」的采购单撤回为草稿，编辑后重新提交
- 创建/详情页 Excel 式表格，供应商按明细行录入与展示

**Non-Goals:**

- 不新增审批状态（复用草稿）
- 不改列表页、不改其他四种单据（assign/return/transfer/recovery）
- 不迁移存量数据（老单行级空 → 展示表头值，继承规则已有）
- 撤回不发送通知（audit_log 留痕即可，避免打扰审批人）

## Decisions

1. **撤回语义 = 待审批 → 草稿**，而非退回已驳回或新造状态——草稿天然可编辑可提交，`submit` 现成；「已驳回」语义属于审批人，避免混淆
2. **后端 `withdraw` action 镜像 submit/resubmit 模式**：`@action(detail=True, methods=['post'])` + `IsAuthenticated/OperationPermission` + `_assert_transfer_operable` + `@audit_log(action='withdraw')`；守卫两条：`审批状态 == '待审批'` 且 `创建人 == 当前用户姓名`，违反返回 400
3. **创建人判定用 `Transfer.创建人` 字符串比对**——Transfer 无创建人 FK，加 FK 是 schema 手术；小组织重名概率低，风险记入 Risks。前端按钮显隐同规则（`doc.创建人 === userStore 姓名`）
4. **编辑接口守卫扩展**：`update` 的 `审批状态 != '已驳回'` 改为 `not in ('已驳回', '草稿')`——草稿编辑复用已驳回编辑的整套语义（单头字段 + items 整体替换、原子、行号重排）
5. **前端撤回按钮**：详情页操作区，`待审批 && 创建人==当前用户` 才渲染；确认弹窗（防误触）→ 调 withdraw → 刷新为草稿态（界面自然露出编辑/提交入口）
6. **Excel 表格改版**：创建页与详情页的明细区改为朴素表格（表头行 + 数据行 + 行内编辑），新增「供应商」列；表头供应商字段从两页移除。存量详情：行级空显示表头值（`line.供应商 || doc.供应商`）

## Risks / Trade-offs

- [创建人按姓名字符串比对，同名员工互相可见对方撤回按钮] → 小组织可接受；审计日志记录真实操作账号可事后追溯；后续要严格再议创建人 FK
- [撤回与审批人操作并发（同时点撤回和通过）] → 后端状态守卫天然串行（先到先得，后到者 400），前端刷新后看到终态即可
- [表头供应商字段保留在模型但界面不可见] → 兼容存量数据的展示继承；不是信息双存（行级为空即明确表示「用表头值」）
- [草稿开放编辑后，误改他人草稿] → 编辑本就在权限范围内（分公司行政等），且草稿未入账无台账风险
