# design — 采购日期个体覆盖

## Context

- 采购日期当前：`get_采购日期 = birth_line.transfer.调拨日期`（serializers.py:114），timeline 同源（views.py:590）——批次口径，无个体层。
- 同构先例：`供应商`（0026）、`规格`（0027）覆盖列 + 三级链（个体 → 出生日批次 → 单头/字典）。前案实测：一张单出生 5 台需 5 个不同日期，批次层无解。

## Decisions

### D1. 照抄供应商/规格模式，两级链即可

日期没有"出生明细行批次值"这一层（日期只在单头），链为：**① 实例.采购日期（个体覆盖）→ ② 出生单.调拨日期**。无出生行的实例：覆盖列有值则显示之，否则 None（与现行为一致）。字段放模型 `规格` 之后（与覆盖列同组）；DB 列序无关紧要。

### D2. 序列化器保持 SerializerMethodField

模型新增同名字段后，序列化器声明的 `采购日期 = SerializerMethodField()` 继续遮蔽（声明字段优先于模型字段），仅改 get 方法体——对外契约不变，前端/导出零感知。

### D3. timeline 同步走链，但"日期"字段不动

timeline 的 birth dict 中 `日期`（单据业务日期）保留单据原值——它描述单据；`采购日期` 走覆盖链——它描述这台设备的采购事实。两者语义本就不同。

### D4. 填充命令沿用纠错纪律

`prod_data_fix_qz2_purchase_dates`：常量表 (编号→date)，断言全存在/属泉州二分，dry-run/apply/幂等，仅写覆盖列（记录性字段，不涉台账）。前案回滚已把入库日期恢复快照，本命令不碰入库日期。

## Risks / Trade-offs

- [覆盖值与批次值无校验冲突] → 个体覆盖语义上就允许与批次不同（正是其存在意义），不做校验
- [migration] → 单列可空新增，无默认回填，PG 秒级
- [展示面遗漏] → 列表/导出走序列化器、标签走 API 值、timeline 已改——四面同链

## Migration Plan

合入 → 常规 `deploy.sh`（migrate 上列）→ 备份 → 填充命令 dry-run → `--apply` → 抽查 7 台（列表/标签/生平显示新日期）+ 其余实例显示不变。
