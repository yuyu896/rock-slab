## Context

当前单据创建页面（采购、领用、回收、调拨等）使用原生 HTML5 `<input type="date">` 组件，用户必须点击小的日历图标才能唤起日期选择器。系统其他部分（如 FilterPanel）已使用 Element Plus 的 `el-date-picker` 组件，具备更好的交互体验和视觉一致性。

本次改造将统一所有单据页面的日期输入组件，提升用户体验并消除组件使用的不一致性。

## Goals / Non-Goals

**Goals:**
- 将所有单据相关页面的日期输入统一为 `el-date-picker` 组件
- 保持现有日期格式（YYYY-MM-DD）和 v-model 绑定逻辑不变
- 确保样式与 Element Plus 其他表单元素一致
- 提供更大的点击区域，整个输入框可点击唤起日期选择器

**Non-Goals:**
- 不修改日期验证逻辑或业务规则
- 不改变日期数据在后端的存储格式
- 不涉及移动端日期选择器的改造（移动端可能有独立实现）
- 不添加新的日期范围限制或快捷选择功能（保持现状）

## Decisions

### 决策 1: 统一使用 Element Plus `el-date-picker`

**选择:** 使用 `el-date-picker` 替换所有原生 `<input type="date">`

**理由:**
- Element Plus 是项目既有 UI 库，无需引入新依赖
- 已在 FilterPanel 等组件中使用，经验证稳定可靠
- 提供统一的样式和交互体验
- 支持更丰富的配置选项（禁用日期、快捷选项等），为未来扩展预留空间

**备选方案及否决理由:**
- 保留原生 input 但调整样式：无法根本解决交互区域小的问题，且浏览器默认样式难以统一
- 使用其他日期选择器库（如 vue3-datepicker）：引入新依赖增加维护成本，且与现有 Element Plus 组件风格不一致

### 决策 2: 保持最小化改动

**选择:** 仅替换组件标签，保持 v-model 绑定、事件处理和验证逻辑不变

**理由:**
- 降低回归风险，业务逻辑不变
- 减少测试范围，仅需验证 UI 交互和日期格式输出
- 与现有代码风格保持一致

### 决策 3: 统一配置 value-format

**选择:** 所有 `el-date-picker` 使用 `value-format="YYYY-MM-DD"` 确保输出字符串格式

**理由:**
- 后端接口期望接收 `YYYY-MM-DD` 格式的字符串
- 与原生 `<input type="date">` 的输出格式保持一致
- 避免前端需要额外的日期格式转换逻辑

## Risks / Trade-offs

### 风险 1: Element Plus 版本依赖
- **风险:** 如果未来 Element Plus 升级导致 `el-date-picker` API 变更
- **缓解:** 项目使用固定版本依赖（package.json），升级前需测试验证

### 风险 2: 样式回归
- **风险:** 不同浏览器下 `el-date-picker` 样式可能与原生 input 有细微差异
- **缓解:** 在主流浏览器（Chrome, Firefox, Edge）测试验证；深色模式下同步测试

### Trade-off: 组件体积
- Element Plus 的日期选择器比原生 input 体积更大（包含弹出面板、日历逻辑等）
- 评估：项目已全局引入 Element Plus，边际成本可忽略；交互体验提升值得这个代价

### 风险 3: 移动端兼容性
- **风险:** `el-date-picker` 在移动端的体验可能不如原生日期选择器（调用系统键盘）
- **缓解:** 本次改动仅针对 PC 端单据创建页面；移动端审批页面如使用原生组件可保持不变（需验证）
