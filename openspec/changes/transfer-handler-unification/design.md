## Context

Transfer 是五类单据（purchase/assign/return/transfer/recovery）共用的单头表，唯一的经办人文本字段名为 `采购经办人`（models.py:84），实际由采购与回收共用；领用/调拨不填它，前端列表把 `创建人` 顶到「经办人」列头下展示。标签口径三处分裂：采购场景创建/详情叫「采购经办人」、列表列头叫「经办人」；回收场景全叫「经办人」但绑定 `采购经办人`。导入模板表头（TYPE_TEMPLATES，views.py:66-87）不含经办人列（导入时经办人=导入操作人），字段重命名无模板兼容风险。`_create_action`（views.py:169）是五类单据唯一建单入口，`创建人` 已在此处做服务端默认（views.py:177-178）。

用户拍板：经办人统一口径=默认创建人（像采购入库：预填当前登录人、可改、选填）；领用上真字段。

## Goals / Non-Goals

**Goals:**

- Transfer 经办人字段更名 `采购经办人` → `经办人`，一名到底（模型/序列化/API key/前端标签/导出列头）
- 服务端默认：建单时经办人为空 → 回填创建人姓名（覆盖移动端与归还 API）
- 采购/回收/领用/调拨四类创建页均有「经办人」输入，预填当前登录人、可改、选填
- 四类列表与导出统一 `经办人 || 创建人` 兜底显示，存量数据不回填

**Non-Goals:**

- 回收台账「经办人=创建人」口径统一（用户明说后续细聊，本变更不动 RecoveryLedger 及其后端取值）
- `RecoveryDetail.vue:40` 回收去向显示 bug（restock 显示成「入回收库」），另行处理
- 归还（return）前端页面（现状无 UI，仅服务端默认顺带覆盖其 API 行为）
- 盘点/调整模块的经办人（独立模型 LedgerAdjustment 已有真字段，口径自洽）
- 存量数据回填或归一命令

## Decisions

### D1：重命名字段而非保留旧名加别名

`采购经办人` 改名 `经办人`（Django RenameField，列名即字段名，SQLite/PG 均元数据级操作）。
- 备选：保留字段名仅统一前端标签——省一次迁移，但模型名/序列化/admin/审计里永久残留「采购」字样，与「一名到底」的统一目标矛盾；且本次无兼容负担（无外部客户端、导入模板无此列），是零成本的重命名窗口。
- API key 变化（`采购经办人` → `经办人`）由前后端同仓同部署吸收；移动端为同一 SPA，无版本偏斜。

### D2：服务端默认收口在 `_create_action`，前端预填仅是 UX

在 `创建人` 默认（views.py:177-178）旁补一行：`if not data.get('经办人'): data['经办人'] = data['创建人']`（置后于创建人默认）。前端四类创建页预填当前登录人姓名仅为可见性，不承担正确性——移动端提交、归还 API 等任何客户端不传经办人时自动获得统一行为。
- 备选：仅前端预填（采购现状）——移动端与未来的导入/接口调用会漏，口径继续分裂。
- 语义细节：用户清空后提交 → 服务端回填创建人。「经办人=默认创建人」口径下空值无意义，回填即对齐口径；字段保持选填（不设必填校验），与采购现状一致。

### D3：存量老单显示层兜底，不回填数据库

领用/调拨存量单及未填经办人的存量回收单，字段值为空。列表/详情/导出统一 `经办人 || 创建人` 渲染，数据库不动。
- 理由：铁律「每样信息只存一处」——经办人默认=创建人是显示语义，回填会制造一份可分叉的存储副本；兜底渲染语义等价且可逆。
- 对照采购列表现状（`item.采购经办人 || item.创建人`）已有此模式，本次只是四类统一。

### D4：调拨同步纳入（统一口径的完备性）

调拨现状与领用同病（列表「经办人」渲染创建人、无字段）。本次一并加字段+预填+兜底，避免同类问题二次立项。调拨特有的 `调出负责人/调入负责人` 是交接双方负责人，语义独立于经办人，维持不动。

### D5：导出列头统一，领用/调拨导出补列

采购导出列头「采购经办人」→「经办人」；领用导出（现有 12 列）与调拨导出（现有 13 列）各补「经办人」列（取值 `经办人 || 创建人`），位置放「备注」前，与采购/回收导出的列序习惯一致。回收导出列头不变，取值字段名随重命名。

### D6：详情页经办人进 TransferDetailLayout 通用 meta，采购 extra 槽位去重

`TransferDetailLayout.vue` 的 meta 行（现有「创建人」）旁增加「经办人」（`经办人 || 创建人`），四类详情统一可见；`PurchaseDetail.vue` extra 槽位里原有的采购经办人条目移除（避免同页两条）。编辑态：采购详情编辑表单字段标签改「经办人」；领用/调拨/回收详情本就无编辑经办人入口，不新增。

## Risks / Trade-offs

- [RenameField 在 PG 上的锁行为] → 单列元数据级重命名，毫秒级 ACCESS EXCLUSIVE，生产表量级（数千行）无感；不走 DML+DDL 混合，无 pending trigger events 风险（见 pg-migration-dml-ddl-atomic 教训，本迁移纯 DDL）
- [遗漏 `采购经办人` 引用导致运行时 500] → 实施 checklist：`grep -rn "采购经办人" backend/ frontend/src --exclude-tests` 收口为零；types/index.ts、importTemplate.ts:108 的固定档案导出表头（非流转单据）如实存疑逐处判断
- [用户清空经办人被服务端回填，感到「改不掉」] → 口径即「默认创建人」，清空=回到默认；UI placeholder 标注「默认创建人」提示语义
- [导出加列改变用户熟悉的列序] → 领用/调拨导出加「经办人」列属口径统一必要变化，放在「备注」前；手验时提示用户新列位置

## Migration Plan

单迁移 `RenameField(Transfer, '采购经办人', '经办人')`，无数据迁移。部署：常规 `bash deploy.sh`（migrate 在流程内）。回滚：代码回退 + 迁移回退对称（RenameField 可逆），字段值全程未动。部署后手验四类单据创建/列表/详情/导出。
