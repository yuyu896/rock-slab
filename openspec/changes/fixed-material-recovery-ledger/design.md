## Context

当前未归档变更 `recovery-restock-and-ledger` 已提出由直接处置回收单派生只读明细台账，实例逐件一行、数量管理按单据行展示。此次讨论进一步确定：该入口命名为“物资处置台账”；直接处置实例从普通实例档案列表及导出移出，但保留原档案和编号，并从台账进入只读详情和完整流转日志。回收单仍承担创建与审批职责。

相关约束：实例档案不得物理删除；直接处置只能由生效单据形成；库存台账继续按库存口径记账；消耗品不进入回收流程；数量管理品目没有单件实例档案。

## Goals / Non-Goals

**Goals:**

- 以“物资处置台账”集中查询已生效的直接处置物资。
- 普通实例档案列表和导出排除有已生效直接处置记录的实例，同时保留不相关的其他退役实例。
- 实例处置记录能只读查看档案和完整流转日志；数量管理处置记录按实际明细和数量追溯。
- 保留现有筛选、分页和导出能力，沿用已有回收数据权限范围。

**Non-Goals:**

- 不改变回收单审批、直接处置生效条件、库存扣减或资产台账记账规则。
- 不删除实例、不回收或重排内部编号，不新增重复存储处置事实的表。
- 不纳入消耗品，不为数量管理物资创建虚构的实例编号、生平或实例记录。
- 不调整其他历史退役实例的展示规则。

## Decisions

### 1. 按已生效处置事实区分普通档案与处置档案

实例是否从普通档案中排除，以其是否关联已生效的直接处置回收明细为准，不以 `status=retired` 单独判断。直接处置实例的原记录、内部编号和历史单据关联继续保留；其他原因退役的实例仍按既有规则查询。

备选方案是隐藏所有退役实例。该方案会同时隐藏与直接处置无关的历史退役档案，无法满足只移动直接处置记录呈现位置的口径，因此不采用。

### 2. 台账从生效单据派生，不复制状态

台账查询和导出沿用回收单明细及实例关联作为数据源，仅包含已审批并实际生效的直接处置单据。待审批、驳回及其他未生效状态不进入台账。这样无需维护另一份台账事实，也不改变单据和库存台账的事务边界。

### 3. 实例与数量管理采用不同粒度

实例管理按单件关联逐条展开，展示原内部编号，并从只读档案详情进入既有实例生平查询。数量管理按真实处置明细行展示品目、分公司、数量、处置方式和源单据；编号/生平不适用，不生成虚构数据。

### 4. 升级现有回收台账入口

复用 `/transfers/recovery/ledger` 及现有台账筛选、分页、导出能力，将菜单和页面名称调整为“物资处置台账”。“回收”菜单下保留“回收单”与“物资处置台账”两个入口。旧台账地址继续可访问并指向新页面，避免书签或已有链接失效。与未归档的 `recovery-restock-and-ledger`、`recovery-stock-source-and-cleanup` 协调时，合并同一页面和 API 的需求，不能生成第二套台账入口或重复接口。

### 5. 只读查看沿用现有实例历史数据与访问范围

复用当前实例档案和生平查询数据，不增设可写操作。处置实例从台账进入的详情视图隐藏所有编辑入口；台账查询、导出、详情和生平读取遵循现有回收/实例读取数据范围，不扩大跨分公司可见性。

## Risks / Trade-offs

- [有效处置关联查询增加普通实例列表和导出的过滤条件] → 用单据关联过滤及必要索引评估查询计划；列表、导出使用同一服务层规则并做回归验证。
- [并行未归档变更仍定义旧台账名称或菜单] → 实施前合并对齐相关 requirements，最终只保留一个页面、一个数据源和兼容路由。
- [生平页面已有可写控件] → 对直接处置上下文采用只读显示模式，并验证不存在编辑、删除或补录入口。
- [状态与处置事实不一致的历史数据] → 以已生效单据关联作为唯一排除依据；发现数据异常时另行走数据核查，不以状态字段猜测处置事实。

## Migration Plan

不需要数据库迁移或生产数据回写。部署应用后由新查询条件决定两个列表的呈现；旧路由继续兼容。回滚应用代码即可恢复原页面和列表呈现，不涉及恢复数据。

## Open Questions

无。菜单层级、纳入对象、数量管理粒度、编号保留和只读追溯范围已在讨论中确定。
