## Context

采购单已有草稿、编辑、提交和创建人撤回规则；后端的通用流转单接口能够创建多种 action type 的草稿，但撤回能力和完整前端入口尚未在各类型间统一。当前草稿仍要求必要单头字段和至少一条有效明细，这一校验口径应保持一致。流转单已有 `created_by` 账号外键，可用于可靠地判断单据创建人。

回收列表备注位于操作列之前，表格使用较宽的最小宽度和横向滚动。较长内容会拉宽表格，操作入口在窄视口下容易离开可视区域。

## Goals / Non-Goals

**Goals:**

- 统一采购入库、领用出库、归还、调拨和回收的草稿、编辑、提交、撤回及驳回后重提规则。
- 仅允许创建人撤回待审批单据；撤回后恢复为可编辑草稿。
- 保证草稿和撤回不发起审批通知、不改变台账或库存。
- 让回收列表的长备注不再挤压操作区，列表操作入口保持可见。

**Non-Goals:**

- 不改变已经生效单据的冲销、退回或历史修正规则。
- 不改变草稿的现有关键字段及有效明细校验，不支持保存缺少必要字段或明细的空表单。
- 不新建归还单的前端录入页面；统一生命周期接口覆盖归还类型，界面能力限于已有录入入口。
- 不迁移或修改历史单据和台账数据。

## Decisions

1. **以流转单通用生命周期作为新能力边界。** 新能力覆盖五种 action type，不把采购入库单独作为模板复制到其他页面。采购单现有行为作为兼容基线，其他类型补齐相同的用户可见操作。

2. **创建人身份由账号外键判定。** 后端以 `created_by` 与当前认证用户比较，不能以姓名、岗位或前端传入的身份字段判定。列表/详情响应提供由服务端计算的 `canWithdraw` 和 `canEditDraft`，前端据此显示操作；接口仍需独立执行相同的权限校验。移动端“我的草稿”查询使用服务端 `mine=true` 按创建账号过滤，不在客户端按姓名筛选。

3. **撤回是“待审批 -> 草稿”的状态转换。** 只允许创建人对待审批单据执行；审批通过、已驳回、已入库和其他状态均拒绝撤回。接口在事务中锁定单据并重新检查状态和创建人，避免撤回与审批并发时覆盖对方状态。撤回成功后保留原明细和业务字段，供创建人继续编辑和提交。

4. **草稿不跳过现有业务校验。** 草稿必须包含现有要求的单头关键字段及至少一条有效明细，但保存和撤回均不得生成台账流水、库存变化或审批通知。提交仍使用现有审批入口和通知路径；驳回后的修改与重提继续使用现有重提语义。

5. **前端沿用采购单交互并覆盖现有入口。** 创建页提供“保存草稿”和“提交审批”；详情/列表按状态和服务端能力字段展示编辑、提交、撤回或驳回后重提入口。移动端审批中心增加本人草稿入口，支持重新打开已有移动端单据类型的草稿；归还类型没有现成录入页，本提案不新增页面。

6. **回收列表限制备注列并固定操作列。** 备注在列表中使用受限宽度和单行省略，完整内容通过既有详情查看；操作列固定在表格右侧。窄屏仍允许表格内容横向滚动，但操作入口不随备注长度离开可视区域。

## Risks / Trade-offs

- [某些历史单据缺少 `created_by`] -> 不允许这类记录执行创建人撤回，并在界面隐藏入口；不得回退到姓名比较。
- [撤回与审批同时发生] -> 在数据库事务中加行锁并再次检查状态，后到操作返回明确的状态错误。
- [五类单据页面实现不完全一致] -> 复用同一套状态能力和服务端 `canWithdraw`，并按单据类型验证创建、草稿、撤回、重提和台账不变行为。
- [固定操作列占用窄屏空间] -> 仅固定必要操作区，长文本在详情查看；在窄视口验证表格和按钮仍可操作。

## Migration Plan

不需要数据库迁移。先发布后端通用撤回校验和响应字段，再发布前端入口；旧客户端即使不展示撤回按钮，也不能绕过后端权限和状态校验。回滚时可回退前后端代码，不需要恢复数据。

## Open Questions

- 实施时需盘点现存各类单据的 Web/移动端创建入口，并将实际存在的入口纳入页面验收；本提案不新增归还单页面。
