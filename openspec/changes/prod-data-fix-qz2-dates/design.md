# design — 泉州二分按内部编号修正入库日期

## Context

实例 `入库日期` 是出生时从采购单 `调拨日期` 落的一份记录性快照（`generate_instances` 写入）。7 个目标实例分属两张出生单（6+1），目标日期互不相同——改单据日期会波及同单全部实例，唯一满足"逐实例不同日期"的层面就是实例档案本身。

日期字段不参与：台账三列、镜像计数、流水重算——`check_ledger_consistency` 与日期无关，修正零对账风险。

## Decisions

### D1. 实例级快照修正，单据不动

仅 `FixedAsset.入库日期` 赋新值（update_fields 单列）。出生单据保持原日期——单据日期代表"该单业务发生日"，实例日期修正为"该台设备实际采购日"，二者语义本就可分（同单购入、日期登记错误正是本单要修的问题）。

### D2. 常量表 + 幂等

`TARGET_DATES = {内部编号: date}` 模块级常量（可被测试 patch）。值相同者跳过（-44 号）；重复执行自然幂等。断言：全部存在、均在泉州二分。

### D3. 通道沿用

本地 commit 不 push（用户工作区有未提交改动）；命令 scp 至服务器、`docker compose run --rm -v` 挂载执行（hz5 前案已验证通道）。

## Risks / Trade-offs

- [编号笔误] → 断言目标全部存在（缺失即中止）；dry-run 打印每条 旧值→新值
- [日期格式歧义] → 常量用 `datetime.date` 对象，解析在代码层完成，不存在运行时歧义

## Migration Plan

本地测试全绿 → 本地 commit（不 push）→ scp → 挂载 dry-run 复核 → 备份 → `--apply` → 抽查 7 个实例新值 → 幂等复证。
