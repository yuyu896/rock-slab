## Context

- 回收在用预检现状分层：前端新建页组件（TransferLinesEditor 的 recoveryOverUse，第 1 案）按调出分公司拉台账在用并拦截提交；后端仅在**审批生效**时经 `apply_document` 行锁充足性终检（LEDGER_INSUFFICIENT → 业务文案）。创建/编辑端点的后端预检缺失，旧缓存页面、Excel 导入、驳回后编辑均可穿透（第 7 案生产排查实证：验收两张"在用 0"回收单建成并卡在待审批）。
- `validate_line_items_instances`（apps/transfers/services.py）是创建/编辑/导入三路径共用的预检函数，签名已含 `from_branch` 与序列化 items——软预检的天然落点。

## Goals / Non-Goals

**Goals:** 后端在创建/编辑回收单时对数量管理品目做（调出分公司×品目）在用软预检，把确定性错误从审批端提前到提交端，文案与审批端同口径。

**Non-Goals:** 不加锁、不动审批端行锁终检（覆盖创建后账面变动的合法竞态）；不改实例管理品目校验（已在预检矩阵）；不改前端（新建页预检已存在）。

## Decisions

1. **落点在 `validate_line_items_instances`**：三路径同口径，单点收口；在既有矩阵校验后追加回收专属分支（action_type=recovery 且 from_branch 非空时）。
2. **软预检语义**：读当前 AssetStock（无锁），合并计量超在用 → ValidationError 400；文案复用审批端 `_recovery_friendly` 的口径（含当前在用/需回收数量与核对提示），但作为独立实现放在预检层（审批端在 ledger 锁内，两处不共享代码路径，仅共享文案风格）。
3. **台账行缺失视为在用 0**：该 (分公司×品目) 从未入账，回收必然错——直接拦。
4. **不影响草稿**：submit（草稿→待审批）不追加校验，保持与创建同口径（草稿本来就是创建路径产生的）。终检兜底不变。

## Risks / Trade-offs

- [软预检与终检间账面变动（创建时在用够、审批时被其他单扣完）] → 预期行为：终检在行锁内拦截并回滚，与现状一致；软预检只消灭"提交时就已确定错"的单据。
- [分公司的台账行在创建后被调拨等改动] → 同上，属账面变动而非预检错误。

## Migration Plan

纯代码收紧，无迁移；部署即生效。此前建成的"在用不足"待审批单不受影响（审批端终检本就会拦）。
