# 设计：实例镜像警告去重与管理方式切换对齐（补丁）

## Context

P2 第二刀已上线（对账双不变量闸门在生产通过）。部署日志暴露：同品目警告按实例数刷屏（A-a00007 一品目 25 行、A-a00011 一品目约 70 行）；且生产存在约 20 个品目 × 数百实例的「数量管理品目挂实例」存量，决断路径无工具支撑。

## Goals / Non-Goals

**Goals:**
- 对账警告一行一品目、带实例条数，聚合统计正确
- 管理方式切换（数量→实例）后有安全对齐路径，不阻塞下一次部署

**Non-Goals:**
- 不自动决断品目管理方式（管理员业务判断）
- 不处理实例→数量方向（该方向不触发镜像执法，警告已提示退役）

## Decisions

### D1 根因：模型默认排序污染聚合/去重

`FixedAsset.Meta.ordering = ['内部编号']` 使 `values_list('item__asset_code').distinct()` 的 SELECT 隐式带上 `内部编号`（用于 ORDER BY），DISTINCT 退化为按两列判重；`values().annotate(Count)` 的 GROUP BY 同样混入排序列、每组拆成单实例（n≡1）。修复：两处查询显式 `.order_by()` 清空默认排序。此前聚合 bug 未造成线上错账是因为消费侧 `+=` 累加恰好抵消（每组多行 n=1 相加=实例数）；修复后每组一行 n=总数，行为等价、查询更省。

替代方案：改模型 Meta 去 ordering——影响面大（所有默认列表排序），否。

### D2 对齐命令语义

`align_ledger_to_instances`：默认预览差异清单（分公司 × 品目 × 列：台账值 → 实例计数 ±delta）；`--confirm` 经 `ledger.apply_adjustment`（唯一写入口）逐条出**非期初**调整单——与迁移 0019 的 is_initial（吸收历史语义）区分，切换对齐是当下的管理动作，流水可追溯。对齐方向以实例计数为准（实物档案为细粒度事实，与 0019 一致）。幂等：无差异零落单。

## Risks / Trade-offs

- [对齐方向选错方向修错账] → 预览先行 + 调整单留痕可逆向冲正；命令不吸收历史（非期初），错操作可用新调整单回滚
- [排序列污染在其它查询复发] → 两处修复处已加注释说明；架构测试不做泛化扫描（误报率高于收益）
