# design — 北京三分/五分电脑序列号清空

## Context

90 个 A-a00011 实例序列号录错待清（员工将重录）。序列号为记录性 CharField：不参与台账/镜像/流水任何不变量；(分公司, 序列号) 唯一约束条件为 序列号≠''，空值豁免——清空不可能违约束，反而重录时同司重复会被约束拦下（防错利好）。展示层：待补录 flag = 序列号为空，列表/导出/盘点清单自动落"待补录"；标签 SN 行空值隐藏，QR 编码内部编号。

## Decisions

### D1. 置空 = 写 ''（与出生默认同形）

`序列号 = ''`（模型 default 同值），仅处理非空者；已空 4 台幂等跳过。单事务、语义计数先取后删惯例不适用（纯 update）。

### D2. 范围固化：两分公司 × A-a00011

两司"电脑"唯一对应 A-a00011（已实测无歧义）；断言目标存在且属两司。他分公司同品目、本司工作手机（A-a00007）零波及。

### D3. 通道与形态沿用

常量固化、dry-run 逐台打印、`--apply`、幂等、末尾对账复核（序列号不影响对账，作统一健康检查）。

## Risks / Trade-offs

- [清错范围] → 品目+分公司双维过滤，dry-run 逐台清单复核
- [重录撞重复] → 唯一约束天然拦截同司重复序列号

## Migration Plan

push → 部署 → 备份 → dry-run（90 条）→ `--apply` → 抽查（90 台序列号空、待补录态、他司/他品目原样）→ 幂等复证。
