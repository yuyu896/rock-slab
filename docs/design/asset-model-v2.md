## 一、病根诊断

现有三表（AssetStock 台账 / Asset 资产列表 / FixedAsset 固定资产）× 五种单据的非对称联动是全部"各种各样的问题"的系统性来源：

| 写入路径 | 台账 | 资产列表 | 固定资产 |
|---|---|---|---|
| 三种导入 | 各自为政 | 各自为政 | 各自为政 |
| 采购/领用/归还/调拨审批 | ❌ 不动 | ✅ | ❌ |
| 回收审批 | ✅ | ✅ | ✅ |

- 数量事实存了三份，不同处理器各动各的子集 → **漂移必然发生且不可发现**；
- Asset 表被双轨滥用（贵重物品一行一件当"准实例"、普通物品一行一批），并滋生品类 hack（电脑序列号列、分公司编号区分手机）；
- 员工上传必须自答"传哪张表"并手抄名称/规格/类目 → 错误率高；
- 编号"不重复"是人的规矩，系统无唯一约束守护，领用/调拨还会自动建行制造重复。

## 二、总纲与铁律

**一句话**：同一件事实只在一个地方存活——库存数量在台账、物品身份在品目字典、贵重物品档案在实例、变动经过在单据，其余一切（状态/充足/总量）都是派生值。

**两条铁律**（P1 落地时写入 CLAUDE.md，全项目强制）：

1. 每样信息只存一处：品目身份在字典、数量在台账、贵重物品档案在实例、变动经过在单据，其余皆为派生。
2. 台账数量的每一次变动必须经流转单（含调整单），禁止任何视图/导入/脚本直接改数量。

## 三、四层架构

```
┌────────────────────────────────────────────────────────┐
│ ① 品目字典 —— 物品的"户口本"（管理员维护，全公司只此一份）      │
│    资产编号 · 名称 · 规格 · 类目 · 管理方式[数量|实例|消耗] · 图片 │
├────────────────────────────────────────────────────────┤
│ ② 资产汇总台账 —— 库存唯一事实源（一行 = 某分公司的某品目）      │
│    在库(存) · 在用(派生) · 回收库(派生) · 总量(派生) · 警戒线   │
├────────────────────────────────────────────────────────┤
│ ③ 固定资产实例 —— 贵重物品"一物一档"（仅实例管理品目展开）       │
│    内部编号 · 序列号(可待补录) · 使用人 · 状态[在库|在用|回收库|退役] │
├────────────────────────────────────────────────────────┤
│ ④ 流转单 —— 唯一写入口（单头 + 明细行）                       │
│    采购入库 · 领用 · 归还 · 调拨 · 回收 · 处置 · 调整           │
└────────────────────────────────────────────────────────┘
```

## 四、核心决策表（13 条）

| # | 决定 | 依据/备注 |
|---|---|---|
| 1 | 品目字典作为编号户籍，管理员维护，唯一约束守护 | 编号本就由管理员统一敲定 |
| 2 | "管理方式"（数量管理/实例管理/消耗品）是品目固有属性，决定单据行为 | 手机电脑等贵重物品需关联到人；2026-08-27 加第三档"消耗品"（纸笔等用掉不回头） |
| 3 | 台账升格为唯一库存事实源，所有单据对称联动 | 治非对称矩阵的漂移病 |
| 4 | Asset 表退役，字段按"品目/实例/流水"三分搬迁，无字段损失 | 双轨用法确认 |
| 5 | 流转单明细行化：单头（谁/何时/为何）+ 明细行（品目×数量×实例） | 一张采购单含全部物品 |
| 6 | 台账直显 在库/在用/回收库/总量 派生列 | 系统目的即方便使用 |
| 7 | 存量迁移：Asset 中数量=1 且有使用人的行 → 实例；其余聚合入台账 | 双轨确认 |
| 8 | 供应商/单价/采购日期属采购单（单据层），字典不存；实例经"出生明细行"追溯 | 修宪一次，勿回退 |
| 9 | 一编号 = 一管理品目。规格分定义性（领用会挑/警戒线分开/价格分开算 → 分编号）与记录性（→ 记采购明细行"本批规格"） | 修订过一次，初版"一号一规格"过粗 |
| 10 | 台账按状态分仓四列；回收拆"入回收库/直接处置"两去向；处置单独立（出售记金额）；领用单增加库存来源（新品库/回收库） | 回收库是数量维度，不是独立表 |
| 11 | UI 风格：Excel 式朴素表格。单据详情 = 一行元信息 + 明细表；拒绝徽章/时间线/装饰 | 用户明确否决单据艺术品化 |
| 12 | 组织树照真实结构：集团→行政大区→行政组→分公司→行政员工；每节点唯一父级，User 只挂分公司；部门是归属标签（分公司×部门字典，下拉），不是树节点；使用人仅记录姓名，不建账号 | 行政组是分公司的父级 |
| 13 | 权限口诀"岗位定操作、任命定范围、特例才单独授予"；supervisor 退役 | 无真人对应 |

## 五、各层详细设计

### 5.1 品目字典

- 字段：资产编号（唯一）、名称、规格（定义性，可为空）、资产类目、物品分类、管理方式、图片、是否租用、默认警戒线、默认供应商（仅预填便利，非事实）。
- 编号粒度 = 具体到规格的管理品目。归组需求（"共多少台笔记本"）由类目/物品分类字段承担。
- 判定测试（写进字典管理页提示）：领用的人会挑规格吗？警戒线需要分开设吗？价格差异大到分开核算吗？任一"是"→分编号。
- 管理方式三档判定（2026-08-27 修订）：贵重需追踪到人 → 实例管理；耐久按量管 → 数量管理；**用掉不回头（纸笔、清洁用品）→ 消耗品**——领用即耗用发放出库，记领用人（签字人）与部门，不进在用。

### 5.2 资产汇总台账

- 一行 = 分公司 × 品目。数量维度四列：在库（唯一存储值）、在用、回收库、总量（三者派生）。
- 库存状态机：

```
                    采购入库
                       ▼
        ┌───────── 新品在库 ◀──归还── 在用(某人手里)
        │             │    ▲              │
        │             │    └──再领用(旧品)──┤
        │             │                回收▼
        │             │              回收库（单独的仓）
        │             │                 │
        └─────────────┴──── 处置(出售/报废/捐赠) ────▶ 出局(总量减少)
```

- 单据 × 数量变动对照：

| 单据 | 台账 | 实例 |
|---|---|---|
| 采购入库 | 在库+N | 生成实例（状态 在库） |
| 领用（新品） | 在库−N，在用+N | 绑定使用人，状态 在用 |
| 领用（来源=回收库） | 回收库−N，在用+N | 从回收库挑实例，绑新使用人 |
| 耗用发放（消耗品领用） | 在库−N（总量随之降） | 无实例；记领用人（签字人）/部门，不进在用 |
| 归还 | 在用−N，在库+N | 状态回在库，使用人清空 |
| 回收（入回收库） | 在用−N，回收库+N | 状态 → 回收库 |
| 回收（直接处置） | 在用−N，总量−N | 实例退役，记方式/金额 |
| 处置单 | 回收库或在库−N，总量−N | 退役；出售记金额 |

- 回收库可设警戒线（积压提醒）；"回收再分配率"为天然报表。
- 消耗品的出口是**耗用发放**：新品在库 ─▶ 出局（在库−N，总量随之降）。消耗品无回收、无实例、不参与在用盘点；调拨可用（在库两边动）；发放流水按部门/领用人可查，报表可出部门消耗统计（2026-08-27 修订）。

### 5.3 固定资产实例

- 内部编号自动生成（`{品目编号}-{序号}`，注意现 count() 方案的并发竞态，改用数据库序列或加锁）。
- 序列号支持"待补录"状态，渐进录入不阻塞流程。
- 领用必须绑定具体实例（实例管理品目）；使用人/部门为记录性文本（非系统用户）。
- 回收/处置不物理删除，状态退役，档案永久保留。

### 5.4 流转单

- 单头：单号、类型、日期、经办人、相关分公司、事由、审批状态/人/时间。
- 明细行：品目 × 数量 × （实例列表，实例管理品目必选）× 本批规格（记录性）× 单价/金额（采购）。
- 采购行金额留空时自动 = 单价 × 数量，手填以手填为准（整批折价可改写）。
- 领用明细行的使用人、部门必填（不分管理方式）；部门按所属分公司字典过滤，表单顺序引导"先选分公司再选部门"。消耗品行同规则——使用人即纸质领用单的签字人，领用时按耗用发放出账（2026-08-27 修订）。
- 回收单去向二选一：入回收库 / 直接处置。处置方式：出售（记金额）/报废/捐赠。
- 回收的唯一入口是回收单审批流（新建 → 待审批 → 通过生效）；不设行内即时回收通道，数据修正走台账调整单。

### 5.5 示例走查：一台笔记本的一生

采购单（含多明细）→ 台账在库+10、生成实例 NB-001-1~10 → 补录序列号 → 领用单绑 NB-001-3 给张三（在库−1 在用+1）→ 归还（在用−1 在库+1，使用人清空）→ 调拨杭州→宁波（两边台账各动、实例分公司跟随）→ 报废回收（实例退役，档案保留）。全程员工无需判断"传哪张表"。

## 六、组织架构

- 真实层级：集团（单例根）→ 行政大区 → **行政组（分公司的父级，组长由某分公司行政兼任）** → 分公司 → 行政员工。
- 现有模型的病：Branch 直挂 Region 又旁挂 Team（两根父线），User 平铺 branch/region/team/leader 四个 FK，集团单例无引用成孤儿。
- 修正：Branch.team 升唯一父级（必填）、删 Branch.region / User.region / User.team / User.leader（沿树推导）、DataScope 改为树遍历、存量 team 为空的分公司先补齐再加约束。

## 七、权限模型

- 现状三套并存（六级角色线 / OperationGrant 9 操作码 / ManagementScope 节点授权），任命与授权脱钩（树负责人字段不参与范围计算），分配需跑四处，无矩阵说明。
- 目标：岗位 = 权限模板（仅预填，不参与运行时鉴权）；任命即授权（树负责人 = 子树范围）；ManagementScope 降级为"额外授权"（跨区兼管等特例）；OperationGrant 为"单独授予"。
- 岗位映射（2026-08-27 修订：负责人/行政合并）：admin→系统管理员、director→大区负责人、leader→行政组长、manager→**分公司行政**（原 manager 分公司负责人与 staff 分公司行政合并，角色码保留 manager，存量 staff 迁移）。分公司行政模板预填八项：管理用户、品目字典、资产管理、审批流转、审批盘点、台账调整、实例管理、统计报表。一个分公司行政约 2 人，不再分级。
- 调拨权限（2026-08-27 修订）：创建调拨单只校验**调出分公司**在操作者授权范围内；调入方不要求授权，但对涉及本分公司的调拨单**只读可见**。台账完整性由单据留痕 + 对账命令兜底。
- 权限分配页交互（2026-08-27 修订）：保存可用条件 = 岗位变化或操作码勾选集与既有授权存在差集；换岗遵循**只补不删**——模板预填与新增照常写入，岗位外既有授权默认保留并提示，显式取消勾选才删除（与 migrate_positions 命令原则统一）。
- 操作码 9 → 约 15（新增 manage_dictionary / manage_instances / adjust_ledger / dispose_assets，审批码按单据类型可分）。细化靠操作码，不靠加角色。
- 体验：分配页三步（选人→选岗位模板→任命节点）+ 实时权限预览；新增权限矩阵页 + 用户生效权限卡（Excel 式呈现）。
- 迁移：role→岗位模板映射，存量授予保留，逐人 diff 预览清单确认后切换。

## 八、前端与 UI 规范

- Excel 式朴素表格优先，一套 data-table 样式全系统复用；单据详情 = 顶部一行元信息 + 明细表，无徽章/时间线/合计加重。
- 列表页改纵向 flex 布局：页面占满内容区高、表格 flex:1 内部滚动、分页钉底（替换魔法数字 `calc(100vh - 340px)`）；默认每页 20→50。
- 新建/创建页（流转单、盘点任务等）为独立页面**撑满内容区宽度**，与列表页同一布局纪律；禁止限宽居中卡片（弹窗观感）（2026-08-27 修订，替换 960px/640px 限宽）。
- 盘点任务详情页：物品明细表（应盘/实盘/差异）+ 盘点流水按人分组（每次提交：人/时间/品目/数量/备注）+ 报告导出 Excel（2026-08-27 修订）。
- 回收单创建页选品目后显示当前**在用数量**并预检拦截；审批端不足报错用业务语言（"回收只针对在用中的资产"）（2026-08-27 修订）。
- 导航演进：资产列表/固定资产两页合并为"台账主视图 + 实例下钻"（P2）。
- 员工上传简表 3-4 列：分公司 + 资产编号 + 数量；编号不在字典整行拒绝并提示相近编号；日常零星用页面字典点选，大批量用 Excel。

## 十、防漂移机制

1. **文字宪法**：本设计书 + P1 时 CLAUDE.md 铁律节；每个会话开工必读。
2. **Spec 合同**：铁律写成 OpenSpec spec（带场景），任何提案必须声明改动哪些 spec，漂移在 diff 可见。
3. **机器执法**：唯一写入口（所有数量变动收敛到 ledger 服务模块）；对账命令（台账 == 单据流水累计，进 pytest 与部署检查）；架构测试（services 之外出现台账写操作即红）。
4. **阶段闸门**：不验收不进下一期；跨期发现设计有误 → 先修宪再写码。
5. **提案审查两问**：这个改动是否让某类信息存了两份？这次数量变动走单据了吗？

## 十一、数据迁移策略

- Asset 双轨拆分：数量=1 且有使用人 → 实例；其余按 (分公司, 编号) 纯 Python 聚合去重入台账（禁止 min(uuid) 等数据库特定聚合——SQLite 测试全绿生产 PG 爆炸的前科）。
- 同编号多规格存量：迁移预览清单暴露，管理员判定"脏数据归一 / 真型号分号"，人工确认后执行。
- 组织迁移：team 为空的分公司补齐归属；部门文本归一为字典（同样出预览清单）。
- 全量备份先行；迁移完成立即跑对账命令。

## 十三、盘点模型（2026-08-27 新增）

- 盘点任务范围 = **分公司 × 资产类目 × 库别**，库别 ∈ {在库, 回收库}；应盘数量取对应台账列，差异调整单修对应列（原实现仅盘在库列）。
- **部门盘点 = 实例盘**：任务可选部门，清单为该部门名下**状态=在用的实例**（仅实例管理品目有实例），**按部门/使用人分组**逐台核对（扫码/点选）；计数单位是"台"而非汇总数量，报告层再汇总到内部编号粒度（应到/实到/缺失明细）。
- 实例盘差异**不自动改账**：盘亏实例报告标记"待跟进"，人工决定后续（重新查找 / 发起回收处置单）；报告页可对盘亏项一键发起回收单（走审批流）。
- 数量管理品目不做部门盘（铁律 1：无持有记录，不新增登记层）。
- 重复盘点规则语义：**累计数量** = 多人分区各数各的 / 逐台扫码逐次累加；**以最后一次为准** = 单人数错重数覆盖。创建页须附场景提示文案。
