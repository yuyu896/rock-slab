## 处置项

### 1. 停止专项脚本误删对账数据

**原风险证据：** 旧版 [`scripts/deploy_reconciliation_v2.sh`](../scripts/deploy_reconciliation_v2.sh) 在询问是否继续前，对 `ReconciliationIssue`、`ReconciliationComparison` 和 `ReconciliationTask` 执行无筛选的 `.all().delete()`。即使选择取消，数据删除也已经发生。

**用户决定：** 对账模块已稳定，今后部署不需要清空生产对账数据。

**已完成的本地处理：** 将此专项脚本改为兼容旧命令的安全入口。它先征求部署确认，确认后只通过 SSH 调用服务器常规 `deploy.sh`；脚本不再连接数据库或删除任何对账记录。尚未执行生产部署。

**验收条件：** 脚本中无对账数据删除或数据库 shell 命令；取消时不连接服务器；确认时只调用常规部署入口。真实部署不属于本次执行范围。

### 2. 清理已删除的 `ACTION_RETURN` 常量引用

**问题范围：** 归还功能已退役，`Transfer.ACTION_RETURN` 已从模型移除，但以下两处仍引用它。执行到该判断时会因属性不存在而抛出 `AttributeError`。

- [`backend/apps/notifications/signals.py`](../backend/apps/notifications/signals.py) 第 118 行。单据缺少业务分公司外键、通知路由需要使用文本字段兜底时，会执行含 `Transfer.ACTION_RETURN` 的判断。
- [`backend/apps/categories/consumable_migration.py`](../backend/apps/categories/consumable_migration.py) 第 161 行。数量品迁移预览遇到没有先被前置条件处理的待审批单据时，会执行归还类型判断。

**建议处理：**

- 移除这两处对 `Transfer.ACTION_RETURN` 的访问。
- 保留通知路由中其他现存单据类型的原有分支行为；不借此调整这些单据的业务规则。
- 保留迁移预览中领用和回收的现有提示；移除归还专属判断后，其他情况沿用已有通用提示。
- 不恢复归还常量、归还 API 或归还操作流程。

**回归验证：**

- 通知路由在缺少业务分公司外键、走文本兜底时不再抛 `AttributeError`，路由结果符合修复前对应现存类型的既有规则。
- 迁移预览包含待审批单据时不再因访问已删除常量而失败；领用和回收提示保持原样，其他情况使用既有通用提示。
- 搜索确认生产代码不再引用 `Transfer.ACTION_RETURN`；归还入口仍保持退役状态。

**处理结果：** 已移除两处失效常量访问。通知路由保留采购取调入方、其他现存类型取调出方的现有规则；迁移预览保留领用和回收的专属提示，其余类型走原有通用提示。

**验收结果：** 通知路由和迁移预览的针对性回归测试通过；生产代码中不再引用 `Transfer.ACTION_RETURN`；归还 API 仍保持退役状态。

### 3. 让部署健康检查失败时返回失败

**原风险证据：** 旧版 [`deploy.sh`](../deploy.sh) 第 117–131 行在健康检查非 200 时只打印“健康检查异常”，随后继续执行脚本并可能以状态码 0 结束。连接错误可能因 `set -e` 提前中止，跳过末尾诊断和回滚锚点。请求未设置明确超时。

**建议处理：**

- 设置有限次数的健康检查重试和明确超时，避免服务刚重启时的短暂未就绪被误报。
- 重试耗尽后输出失败状态、HTTP 结果和日志查看指引，并返回非零退出码。
- 代码回滚和数据库恢复仍由单独的发布决策控制；不要在未审阅数据库迁移可逆性的情况下自动恢复数据库。

**验收条件：** 模拟健康检查成功时脚本返回 0；模拟持续失败时返回非零；超时有界，回滚锚点仍可见。验收在隔离环境完成，不连接生产服务。

**处理结果**

- 重启后立即探测原有 `http://localhost:8002/api/health/`，整体等待预算为 60 秒。每次连接超时为 3 秒，请求总超时最多 5 秒，重试间隔最多 5 秒。请求和等待时长均受剩余预算限制。
- 同时满足 `curl` 成功退出和 HTTP 200 时输出部署成功并返回 0。HTTP 异常、连接错误和超时均进入重试，等待耗尽后输出部署失败并返回 1。
- 失败时报告最后一次 HTTP 状态码、`curl` 退出码和后端日志查看命令。成功与失败路径均先输出部署前 commit、备份路径和回滚参考命令，再返回最终状态。

**验收结果**

新增 [`scripts/tests/test_deploy_health.sh`](../scripts/tests/test_deploy_health.sh)，提取实际健康检查尾段并模拟请求和时间推进。8 个场景全部通过，覆盖首次成功、HTTP 503 后恢复、连接错误后恢复、持续 HTTP 503、持续连接错误、持续超时、HTTP 200 但传输失败，以及接近截止时缩短请求和等待时长。验证了退出状态、失败诊断和回滚锚点。脚本语法检查与差异空白检查通过。未执行生产部署。

### 5. 分类并修复测试基线

**本次复核结果（2026-11-25）：** 后端全量测试为 **1321 项，其中 1243 通过、68 失败、10 跳过**；前端 Vitest 为 **429 项，其中 401 通过、28 失败**。前端生产构建通过。当前数字对应复核时的工作区状态，工作区已有的其他未提交修改不属于本项。

**失败分类：**

- **已确认的真实生产缺陷：** 消耗品迁移流程写入 `apps.categories.models.ConsumableMigrationRun`，对应表为 `categories_consumablemigrationrun`；台账检查命令却读取 `apps.assets.models.ConsumableMigrationRun`，对应表为 `assets_consumable_migration_run`。当前生产代码没有同步写入后者的路径，导致 `quantity_until` 为空，历史迁移前的领用单可能按错误的消耗品规则重放。失败用例 `tests/test_ledger_migration_and_guard.py::TestCheckLedgerConsistency::test_historical_assignment_uses_quantity_rule_after_consumable_migration` 已稳定复现该问题。
- **测试数据契约过期：** 29 项对账测试缺少当前必填的 `billing_period`；17 项品目分类映射、级联或必填字段测试仍使用旧数据约定。这些项目需要按当前接口和模型契约修正测试数据，再重新判断是否存在产品行为问题。
- **退役功能的过期断言：** 19 项后端测试仍依赖已退役的归还功能，其中包含已删除的 `ACTION_RETURN`、旧接口状态码，以及历史归还记录是否继续进入报表的业务口径问题。测试不能通过恢复退役功能来修复。
- **前端契约、权限和测试替身问题：** 28 项前端失败分布在请求参数、权限语义、错误文案、页面标题、DOM 包装器、二维码和导出 mock 等路径，需要按具体路径分别确认。
- **测试配置问题：** `backend/pytest.ini` 中的 `override_ini` 不是 pytest 支持的配置项，当前只产生 `Unknown config option` 警告，不能据此确认测试使用了预期的内存 SQLite 数据库。

**分项处理顺序：**

1. 先确定 `ConsumableMigrationRun` 的唯一正式模型及历史数据归属。若保留 `categories` 模型，应让台账检查读取该模型并补跨模块回归测试；若正式迁移到 `assets`，则需要同步修改写入端并处理已有 `categories` 记录。不能只修改测试绕过错表问题，也不能在未核实历史数据前删除 `assets` 表或其迁移。
2. 修正 pytest 配置，单独验证测试数据库设置，再重新取得后端基线。
3. 按测试数据契约、退役功能、前端请求与 mock、权限语义和环境限制分别处置，避免一次性修改全部失败。
4. 对仍待确认的历史归还报表口径、权限语义和接口返回字段保留业务决策记录。

**验收条件：** 每个失败都有分类和处置结论；台账迁移路径有针对性的跨模块回归测试；测试配置有效且数据库设置已验证；已确认的产品路径通过回归测试；剩余失败均有记录的业务或环境原因；后端和前端全量套件结果可重复。

### 6. 将 Django 升级到受支持版本

**证据：** [`backend/requirements.txt`](../backend/requirements.txt) 将 Django 限制为 `>=5.1,<5.2`。Django 官方列出 5.1 的扩展支持于 2025-12-03 结束；截至本文件日期，该系列不再接收安全修复。5.2 LTS 的安全支持截至 2028 年 4 月。[官方支持版本表](https://www.djangoproject.com/download/)。

**建议处理：**

- 目标优先评估 Django 5.2 LTS，并选用该系列最新补丁版本；确认 Python 3.11、Django REST Framework 及其余第三方包的兼容性。
- 单独开升级变更，先在当前版本开启并处理 Django 弃用警告，再阅读 5.2 发布说明和不兼容变更。
- 在隔离环境验证完整测试、迁移、静态文件、认证、文件上传、数据库连接和生产配置；准备回滚方案后再安排预发布。
- 不能只改依赖约束就认为完成升级；部署前应核实实际安装版本和服务启动版本。

**验收条件：** 依赖锁定到受支持版本；完整验证通过或所有残余失败有明确接受记录；预发布环境通过关键业务验收；生产发布和回滚另行审批。
